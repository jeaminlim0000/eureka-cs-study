## 1. 인터페이스와 다형성

### 핵심 개념

- **인터페이스(Interface)**: 구현 객체가 외부에 제공할 행위(메서드 규격)의 계약(Contract)입니다. 호출하는 쪽(클라이언트)은 구체 클래스가 아닌 인터페이스에만 의존합니다.
- **다형성(Polymorphism)**: 동일한 인터페이스 타입의 변수로 메서드를 호출하더라도, **실행 시점(Runtime)**에 주입된 실제 구현 객체에 따라 서로 다른 동작이 수행되는 객체지향의 특성입니다.

### 결제 시스템 예시 코드

```java
// 1. 역할(인터페이스) 정의
public interface PaymentProcessor {
    PaymentResult pay(long amount);
}

// 2-1. 구현체 A (토스페이)
@Component
public class TossPaymentProcessor implements PaymentProcessor {
    @Override
    public PaymentResult pay(long amount) {
        // 토스페이 결제 API 연동 로직
        return new PaymentResult(true, "Toss 결제 완료: " + amount + "원");
    }
}

// 2-2. 구현체 B (네이버페이)
@Component
public class NaverPaymentProcessor implements PaymentProcessor {
    @Override
    public PaymentResult pay(long amount) {
        // 네이버페이 결제 API 연동 로직
        return new PaymentResult(true, "Naver 결제 완료: " + amount + "원");
    }
}

// 3. 클라이언트(OrderService)는 인터페이스에만 의존
@Service
public class OrderService {
    private final PaymentProcessor paymentProcessor;

    public OrderService(PaymentProcessor paymentProcessor) {
        this.paymentProcessor = paymentProcessor;
    }

    public void processOrder(long amount) {
        // 런타임에 주입된 구현 객체(Toss or Naver)의 pay()가 동적 바인딩(Virtual Method Dispatch)되어 실행됨
        PaymentResult result = paymentProcessor.pay(amount);
        System.out.println(result.message());
    }
}
```

### 다형성 활용 시 주의해야 할 엣지 케이스 (Edge Cases)

1. **동적 바인딩 vs 정적 바인딩 (필드 및 static 메서드)**:
   - 인스턴스 메서드는 런타임 객체에 따라 동적 바인딩(Dynamic Binding)되지만, **필드(멤버 변수)나 `static` 메서드는 컴파일 시점의 선언 타입(정적 바인딩)을 따라갑니다.** 따라서 인터페이스나 상위 클래스의 필드/정적 메서드를 다형성 목적으로 오버라이드하려 하면 의도와 다르게 동작합니다.
2. **다운캐스팅(Downcasting)과 `ClassCastException`**:
   - 특정 구현체의 메서드가 필요하다고 해서 인터페이스 타입을 특정 구체 클래스로 강제 캐스팅(`(TossPaymentProcessor) paymentProcessor`)하면, 다른 구현체가 주입되었을 때 런타임에 `ClassCastException`이 발생합니다. 이는 다형성의 취지(DIP, OCP)를 깨뜨리는 안티패턴입니다.
3. **인터페이스 분리 원칙(ISP) 위반**:
   - 인터페이스에 너무 많은 메서드를 몰아넣으면, 특정 구현체는 필요하지도 않은 메서드를 억지로 빈 구현(`throw new UnsupportedOperationException()`)으로 채워야 하는 문제가 생깁니다. 작고 구체적인 역할 인터페이스로 쪼개야 합니다.

## 2. IoC와 생성자 주입

### 핵심 개념

- **IoC (Inversion of Control, 제어의 역전)**:
  - 전통적인 방식: 프로그램의 제어 흐름(객체 생성, 라이프사이클 관리, 의존 객체 연결)을 개발자가 작성한 비즈니스 로직 코드 내부에서 직접 `new` 키워드로 결정함.
  - IoC 방식: 객체의 생성과 연결, 생명주기 관리 권한을 개발자가 아닌 **외부 구성 요소(스프링 IoC 컨테이너 / 프레임워크)**에 위임하는 설계 원칙.
- **DI (Dependency Injection, 의존성 주입)**:
  - IoC를 구현하는 대표적인 디자인 패턴. 객체가 스스로 의존성을 생성하지 않고, **외부에서 생성된 의존 객체를 전달(주입)받아 사용**하는 방식.

### 제어 흐름 비교 및 예시

```java
// [전통적 제어 - 개발자가 직접 제어]
public class TraditionalOrderService {
    private final PaymentProcessor paymentProcessor;

    public TraditionalOrderService() {
        // 객체 내부에서 직접 구현체를 new 함 -> DIP/OCP 위반, 강한 결합, 단위 테스트 어려움
        this.paymentProcessor = new TossPaymentProcessor();
    }
}

// [IoC / DI 적용 - 제어를 외부에 위임]
public class InjectedOrderService {
    private final PaymentProcessor paymentProcessor;

    // 필요한 부품을 생성자 매개변수로 명시하고 외부에서 주입받음
    public InjectedOrderService(PaymentProcessor paymentProcessor) {
        this.paymentProcessor = Objects.requireNonNull(paymentProcessor, "paymentProcessor는 null일 수 없습니다.");
    }
}
```

### DI 외의 IoC 형태 (DI가 아니어도 IoC인 경우)

- **템플릿 메서드 패턴 (Framework Callbacks)**: 상위 추상 클래스나 프레임워크(예: JUnit, 서블릿 컨테이너)가 전체 라이프사이클 흐름(`init()`, `@Test`, `destroy()`)을 제어하고, 개발자가 작성한 하위 구현 코드는 프레임워크에 의해 불려 다니는(Hollywood Principle: *"Don't call us, we'll call you"*) 대표적인 IoC입니다.
- **Service Locator 패턴 (안티패턴)**: 컨테이너에서 의존 객체를 직접 조회(`container.getBean("paymentProcessor")`)해 오는 방식. 제어의 역전은 일어나지만, 의존성이 클래스 외부 인터페이스(생성자)에 드러나지 않고 숨겨져 있어 결합도가 높아지고 테스트가 어려워집니다.

### 생성자 주입을 사용하는 이유 및 엣지 케이스

1. **불변성(Immutability) 보장**:
   - 의존 필드를 `final`로 선언할 수 있어, 객체 생성 이후 의존성이 임의로 변경되는 것을 방지합니다.
2. **순수 POJO 단위 테스트 용이성**:
   - 무거운 Spring 컨테이너(`@SpringBootTest`) 없이도 Mockito 목 객체나 가짜 구현체(`FakePaymentProcessor`)를 생성자에 직접 넘겨 0.01초 만에 실행되는 단위 테스트 작성이 가능합니다.
3. **엣지 케이스: 순환 참조(Circular Dependency) 조기 감지**:
   - `OrderService`가 `MemberService`를 의존하고, `MemberService`가 `OrderService`를 의존하는 순환 참조가 있을 때:
     - **필드 주입/수정자 주입**: 일단 객체를 생성한 뒤 나중에 주입하므로, 애플리케이션이 정상 실행되었다가 런타임에 메서드 호출 시 `StackOverflowError`로 터질 수 있음.
     - **생성자 주입**: 애플리케이션 부트스트랩(구동) 시점에 객체를 생성하려다 즉시 `BeanCurrentlyInCreationException`을 던지며 **Fail-fast**하게 실패하여 설계를 바로잡을 수 있음.

## 3. Spring 빈 등록과 주입 대상 선택

### 핵심 개념

- **Spring Bean (스프링 빈)**: Spring IoC 컨테이너(ApplicationContext)에 의해 인스턴스화, 조립, 관리되는 객체 (기본적으로 싱글톤 스코프로 관리).
- **빈 등록 방식 2가지**:
  1. **컴포넌트 스캔 (자동 등록)**: `@Component` 및 그 특화 어노테이션(`@Service`, `@Repository`, `@Controller`, `@RestController`, `@Configuration`)을 클래스에 붙이면 스프링이 시작할 때 패키지를 스캔해 자동으로 빈으로 등록.
  2. **자바 설정 클래스 (수동 등록)**: `@Configuration` 클래스 내부에서 `@Bean` 메서드를 통해 객체를 생성하고 반환하여 등록 (외부 라이브러리 클래스나 환경별 동적 빈 등록 시 주로 사용).

### 동일 인터페이스 구현체가 여러 개일 때의 충돌 및 해결

`PaymentProcessor` 인터페이스의 구현체인 `TossPaymentProcessor`와 `NaverPaymentProcessor`가 둘 다 빈으로 등록되어 있다면, Spring은 어떤 빈을 주입해야 할지 몰라 **`NoUniqueBeanDefinitionException`** 예외를 던집니다.

```text
Parameter 0 of constructor in OrderService required a single bean, but 2 were found:
- tossPaymentProcessor: defined in file [TossPaymentProcessor.class]
- naverPaymentProcessor: defined in file [NaverPaymentProcessor.class]
```

#### 해결 방법 및 우선순위 규칙

1. **`@Primary` 사용 (기본값 설정)**:
   - 특정 구현체에 `@Primary`를 붙여두면, 특별한 지정이 없을 때 기본 우선권을 갖습니다.
2. **`@Qualifier` 사용 (명시적 지정)**:
   - 빈 선언부와 주입 지점에 `@Qualifier("별칭")`을 부여하여 특정 빈을 명시적으로 매칭합니다.
3. **필드명/파라미터명 매칭**:
   - 생성자 매개변수 이름을 빈 이름과 일치시키면(`PaymentProcessor tossPaymentProcessor`) 매칭됩니다. 단, 이름 리팩토링 시 취약하므로 `@Qualifier` 사용이 권장됩니다.

```java
@Service
public class OrderService {
    private final PaymentProcessor paymentProcessor;

    // @Qualifier를 생성자 파라미터에 명시
    public OrderService(@Qualifier("tossPaymentProcessor") PaymentProcessor paymentProcessor) {
        this.paymentProcessor = paymentProcessor;
    }
}
```

> **우선순위 엣지 케이스**:
> `@Primary`와 `@Qualifier`가 동시에 존재하는 경우, **`@Qualifier`가 더 구체적인 지정자이므로 항상 `@Primary`보다 우선순위가 높습니다.**

### Lombok의 역할과 Spring DI의 관계

- **Lombok (`@RequiredArgsConstructor`)**:
  - 스프링 프레임워크의 기능이 아니라, **자바 컴파일러 어노테이션 프로세서(Annotation Processor)**입니다.
  - 컴파일 타임에 `final`이나 `@NonNull`이 붙은 필드를 매개변수로 받는 생성자 바이트코드를 자동으로 생성해 줍니다.
- **Spring과의 결합 (Spring 4.3+)**:
  - Spring 4.3부터 클래스에 **생성자가 단 하나만 존재하면 `@Autowired` 어노테이션을 생략**해도 스프링이 자동으로 해당 생성자를 통해 의존성을 주입합니다.
  - 따라서 `@RequiredArgsConstructor`를 붙이면 Lombok이 생성자를 만들어 주고, 스프링은 그 단일 생성자를 보고 DI를 수행하여 반복적인 보일러플레이트 코드 없이 간결하게 생성자 주입이 완성됩니다.
