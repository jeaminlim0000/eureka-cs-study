# 1주차 Discussion 댓글 예시

각 주제의 질문 글 아래에 필요한 댓글만 복사해 사용합니다. 첫 답변과 수정 답변은 팀원이 자기 경험과 판단으로 작성합니다. 아래 문장은 학습용 알림 서비스 예시에 대한 연습 답변입니다.

## 주제 1 · 인터페이스와 다형성

### 팀원의 첫 답변 예시

인터페이스 타입으로 호출해도 실제로 들어 있는 객체의 구현 메서드가 실행됩니다.

학습용 알림 코드에서는 서비스가 `NotificationSender`를 받고, `notifyUser()` 안에서 `send()`를 호출합니다. 이메일 객체가 들어가면 이메일 구현이, 문자 객체가 들어가면 문자 구현이 실행됩니다. 발송 방식이 바뀌어도 호출하는 서비스의 메서드는 그대로 사용할 수 있습니다.

### 출제자가 이어서 물을 꼬리 질문

구현체가 하나뿐이고 앞으로도 바꿀 요구가 없다면 같은 인터페이스를 유지하겠어요? 어떤 이점과 유지 비용을 비교하실 건가요?

### 출제자가 올릴 AI 참고 답변

인터페이스는 호출 가능한 동작의 계약을 표현합니다. 일반적인 인스턴스 메서드 호출은 실제 객체의 구현에 따라 실행됩니다.

인터페이스로 의존성을 선언하면 서비스에서 구체 구현을 직접 사용하는 부분을 줄일 수 있습니다. 다만 인터페이스를 따로 관리하는 비용도 있으므로, 실제로 바뀌는 경계나 테스트에서 대체할 필요가 있는지를 함께 설명하면 좋습니다.

[Java 인터페이스와 상속](https://docs.oracle.com/javase/tutorial/java/IandI/index.html)

### 답변자가 비교 후 남길 댓글 예시

처음에는 구현체를 바꿀 수 있다는 장점만 설명했습니다. 실제로 어떤 변경 요구가 있었는지와 인터페이스를 추가하는 비용은 빠뜨렸습니다.

다시 답한다면 “발송 방식이 바뀌는 요구가 있어서 서비스가 발송 인터페이스에 의존하도록 했습니다. 구현이 바뀔 가능성과 테스트에서 대체할 필요가 낮다면 구체 클래스를 직접 사용하는 방법도 비교하겠습니다”라고 설명하겠습니다.

## 주제 2 · IoC와 생성자 주입

### 팀원의 첫 답변 예시

DI는 객체가 필요한 의존성을 외부에서 전달받는 방식입니다. 서비스가 생성자에서 직접 이메일 발송 객체를 만들면 그 구현과 객체 생성 방식까지 알아야 합니다. 생성자로 받으면 외부에서 이메일이나 문자 구현을 전달할 수 있습니다.

학습용 코드에서 `NotificationService`는 `NotificationSender`를 생성자로 받습니다. 일반 Java 코드에서는 호출자가 객체를 만들고 넘깁니다. Spring 빈으로 사용하면 컨테이너가 등록된 발송 빈을 서비스 생성자에 전달합니다.

### 출제자가 이어서 물을 꼬리 질문

그 서비스가 외부 API를 실제로 호출하지 않게 테스트하려면 어떤 객체를 생성자에 전달하겠어요? 성공과 실패를 각각 어떻게 확인하겠어요?

### 출제자가 올릴 AI 참고 답변

DI는 객체가 필요한 의존성을 외부에서 전달받는 방식입니다. 생성자 주입은 필수 의존성을 생성자에 드러내고, 테스트에서 의존 객체를 바꿔 전달하기 쉽게 합니다.

일반 Java 코드에서도 생성자 주입을 할 수 있고, Spring에서는 컨테이너가 빈을 만들면서 의존 객체를 연결합니다. Lombok의 `@RequiredArgsConstructor`는 생성자를 만들며, Spring은 그 생성자를 이용해 객체를 전달합니다.

테스트에서는 고정 응답을 주거나 지정한 예외를 던지는 테스트 대역을 전달해 서비스의 반응을 확인할 수 있습니다. 실제 외부 API의 통신 동작은 별도로 확인해야 합니다.

[Spring 의존성 주입](https://docs.spring.io/spring-framework/reference/core/beans/dependencies/factory-collaborators.html)

### 답변자가 비교 후 남길 댓글 예시

처음 답변에서는 객체를 교체할 수 있다는 점까지 설명했지만, 어떤 실패를 재현할지는 생각하지 못했습니다.

다시 답한다면 “외부 클라이언트 대신 지정한 예외를 던지는 대역을 생성자로 전달하고, 서비스가 해당 실패를 어떤 결과로 반환하거나 전파하는지 검증하겠습니다”라고 덧붙이겠습니다. 실제로 작성한 테스트가 있다면 그 테스트의 입력과 기대 결과도 함께 설명하겠습니다.

## 주제 3 · Spring 빈 등록과 주입 대상 선택

### 팀원의 첫 답변 예시

Spring 빈은 컨테이너가 생성과 의존성 연결 등을 관리하는 객체입니다. 컴포넌트 스캔이나 `@Bean` 메서드 등으로 등록할 수 있습니다. 생성자가 하나라면 Spring은 `@Autowired` 없이도 그 생성자를 사용해 의존 객체를 주입할 수 있습니다.

주어진 오류는 후보가 여러 개여서 하나를 결정하지 못한 상황이므로, 서비스 생성자 타입과 해당 타입으로 등록된 빈을 확인하겠습니다. 알림 서비스에서 이메일 구현을 명시해야 한다면 생성자 매개변수에 `@Qualifier`를 지정하겠습니다. 여러 곳에서 기본으로 고를 구현이라면 `@Primary`도 검토하겠습니다.

### 출제자가 이어서 물을 꼬리 질문

Lombok이 생성자를 만드는 코드라면 `@Qualifier`가 실제 주입 지점까지 전달되는지도 어떻게 확인하시겠어요?

### 출제자가 올릴 AI 참고 답변

`@Qualifier`는 주입 지점에서 사용할 후보를 좁히고, `@Primary`는 단일 값 주입 후보가 여러 개일 때 우선할 빈을 지정하는 데 사용합니다.

필드에 적은 어노테이션이 Lombok이 생성한 생성자 매개변수로 전달되는지는 설정과 생성 결과를 확인해야 합니다. 특정 구현을 명시적으로 보여주려면 생성자를 직접 작성하고 매개변수에 `@Qualifier`를 두는 방법을 사용할 수 있습니다.

[Spring 주입 후보 선택](https://docs.spring.io/spring-framework/reference/core/beans/annotation-config/autowired-qualifiers.html)

### 답변자가 비교 후 남길 댓글 예시

처음에는 어노테이션을 어디에 붙이는지 자세히 생각하지 않았습니다. 실제로 Spring이 사용하는 주입 지점이 생성자 매개변수이므로, 최종 생성된 코드나 애플리케이션 시작 테스트로 선택된 빈을 확인해야 한다는 점을 추가하겠습니다.
