## 1. 응답 시간·p95/p99·오류율

**면접 질문** · 평균 응답 시간은 비슷한데 p99만 올랐습니다. 무엇을 확인하겠어요?

**꼬리 질문** · 특정 인스턴스 한 대에서만 문제가 보인다면 배포 버전, 트래픽 분배, 의존 서비스 중 무엇을 어떻게 비교하겠어요?

<details>
<summary>예시 답변 보기</summary>

같은 기간과 요청 범위에서 p99가 올랐다면 일부 요청의 꼬리 지연이 늘어난 상황인지 살펴보겠습니다. 먼저 어떤 API와 인스턴스에서 언제부터 늘었는지, 요청 수가 충분한지 확인하겠습니다. 같은 시간대의 오류율과 배포·트래픽 변화를 비교하고, 느린 요청의 트레이스를 정상 요청과 대조해 추가 시간이 생긴 구간을 찾겠습니다.

</details>

## 2. CPU·메모리가 정상인데 서버가 느린 상황

**면접 질문** · 서버 CPU와 메모리 사용률은 평소와 비슷한데 API가 느려졌습니다. 어디서부터 보겠어요?

**꼬리 질문** · SQL 실행 시간은 정상이고 커넥션 대기만 늘었습니다. 풀 크기를 늘리기 전에 무엇을 확인하시겠어요?

<details>
<summary>예시 답변 보기</summary>

먼저 느려진 시점, API, 인스턴스를 좁히고 p95·p99, 요청량, 오류율을 같이 보겠습니다. 그다음 느린 요청에서 애플리케이션 진입 전 대기, DB 커넥션을 얻는 대기, SQL 실행, 외부 호출 중 어느 구간이 길어졌는지 나누겠습니다. 커넥션 대기만 늘었다면 풀의 사용 중인 연결과 대기 요청을 보고, 긴 트랜잭션이나 외부 호출 때문에 연결을 오래 잡고 있는지 확인하겠습니다.

</details>

## 3. 로그와 트레이스로 본인 코드 설명

**면접 질문** · 본인이 만든 API가 느려졌다면 코드의 어느 부분을 보고, 어느 지점에 시간을 남기겠어요?

**꼬리 질문** · 운영 로그에 이미 남는 정보는 무엇인가요? 추가로 계측할 지점 하나만 고른다면요?

<details>
<summary>예시 답변 보기</summary>

예를 들어 상담 요청에서 DB 조회와 외부 응답 생성 호출이 이어진다면, 먼저 두 호출을 하는 서비스 메서드를 보여드리겠습니다. 요청 ID로 전체 경로를 묶고, DB 연결 대기와 쿼리 실행, 외부 호출 각각의 시간을 볼 수 있게 하겠습니다. 재시도가 있다면 시도별 시간과 결과도 구분해 전체 지연이 한 번의 느린 호출에서 왔는지 반복 호출에서 왔는지 확인하겠습니다.

</details>
