## Redis를 캐시로 쓰는 이유

Redis는 메모리 기반 Key-Value 저장소로, DB 조회 결과처럼 자주 읽고 변경 빈도가 비교적 낮은 데이터를 빠르게 제공하는 데 적합합니다. 캐시는 원본 DB를 대체하는 저장소가 아니라 DB 부하와 응답 시간을 줄이는 보조 계층입니다.

## Cache-Aside

Cache-Aside는 애플리케이션이 먼저 Redis를 조회하고, 없으면 DB에서 조회한 뒤 Redis에 저장하는 방식입니다.

```text
Redis 조회 → Cache Hit: 캐시 값 반환
Redis 조회 → Cache Miss: DB 조회 → Redis 저장(TTL) → 반환
```

데이터 수정 시에는 DB를 먼저 변경하고 관련 캐시를 삭제하거나 갱신해야 합니다. 캐시와 DB 값이 짧은 시간 달라질 수 있다는 점을 고려해야 합니다.

## TTL과 Cache Stampede

TTL은 캐시 데이터의 만료 시간입니다. TTL이 없으면 오래된 값이 남을 수 있고, 너무 짧으면 Cache Miss가 잦아집니다.

여러 요청이 동시에 만료된 키를 조회하면 모두 DB를 읽는 Cache Stampede가 생길 수 있습니다. 만료 시간에 랜덤 값을 더하거나, 한 요청만 DB를 조회하도록 락을 사용하거나, 미리 갱신하는 방식으로 완화할 수 있습니다.

## Java·Spring 연결

Spring에서는 `@Cacheable`, `@CacheEvict` 또는 RedisTemplate을 사용할 수 있습니다. 하지만 애노테이션만 붙이는 것으로 일관성이 보장되지는 않으므로, 어떤 데이터에 캐시를 둘지와 갱신·삭제 시점을 명확히 정해야 합니다.

## 발표 중 확인한 질문

**Redis 캐시를 추가했는데도 DB 부하가 순간적으로 커질 수 있는 이유와 해결 방향을 설명해 주세요.**  
같은 인기 키의 TTL이 동시에 만료되면 여러 요청이 한꺼번에 DB를 조회하는 Cache Stampede가 발생할 수 있습니다. TTL에 랜덤 값을 더해 만료를 분산하고, 필요한 경우 분산 락·요청 병합·사전 갱신을 적용합니다. 다만 락은 복잡도와 장애 상황을 늘릴 수 있어 인기 키처럼 필요한 구간에 제한적으로 사용해야 합니다.
