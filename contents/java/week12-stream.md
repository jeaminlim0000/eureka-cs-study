# Week12 Java 심화 — Stream

> 발표자: 재민　 발표일: 2026.09.29　 주차 Issue: [#17](https://github.com/jeaminlim0000/eureka-cs-study/issues/17)

## 1. 핵심 개념

**Stream**은 컬렉션이나 배열 등의 데이터를 필터링·변환·정렬·집계하는 처리 흐름을 표현하는 Java API입니다.

예를 들어 주문 목록에서 결제가 완료된 주문만 골라내고, 주문 번호를 추출해 새로운 목록으로 만들 수 있습니다.

```text
데이터 소스 → 중간 연산 → 최종 연산
주문 목록 → 결제 완료 주문 필터링 → 주문 번호 목록 생성
```

| 연산 | 역할 | 구분 |
|---|---|---|
| `filter` | 조건에 맞는 요소 선택 | 중간 연산 |
| `map` | 요소를 다른 값이나 객체로 변환 | 중간 연산 |
| `sorted` | 정렬된 순서로 요소 처리 | 중간 연산 |
| `distinct` | `equals()` 기준으로 중복 제거 | 중간 연산 |
| `count` | 요소 개수 계산 | 최종 연산 |
| `toList` | 결과를 리스트로 수집 | 최종 연산 |

`filter`나 `map` 같은 중간 연산은 처리 방법을 연결하고, `toList`나 `count` 같은 **최종 연산이 실행될 때 실제 처리가 시작됩니다.** 이를 지연 연산이라고 합니다.

Stream은 데이터를 보관하는 컬렉션 자체가 아니라 데이터를 처리하는 흐름입니다. 한 번 사용한 Stream은 다시 사용할 수 없으므로, 같은 컬렉션을 다시 처리하려면 새로운 Stream을 만들어야 합니다.

일반적으로 원본을 읽어 결과를 만드는 데 사용하지만, Stream이 원본이나 내부 객체를 자동으로 보호하는 것은 아닙니다. 람다 안에서 객체를 수정하면 원본에도 영향을 줄 수 있으므로 주의해야 합니다.

## 2. Java / Spring 사용 예시

Spring Service에서 조회한 주문 목록이 `List<Order> orders`에 들어 있다고 가정하면, 결제가 완료된 주문의 번호만 다음과 같이 추출할 수 있습니다.

```java
List<Long> paidOrderIds = orders.stream()
        .filter(order -> order.getStatus() == OrderStatus.PAID)
        .map(Order::getId)
        .toList();
```

- `stream()`으로 주문 목록의 처리 흐름을 만듭니다.
- `filter()`로 결제가 완료된 주문만 선택합니다.
- `map()`으로 주문 객체에서 주문 번호를 추출합니다.
- `toList()`로 결과를 리스트에 모읍니다.

이 예시는 주문 객체를 수정하지 않고 필요한 값만 추출합니다. 같은 방식으로 Entity 목록을 응답용 DTO 목록으로 변환할 수도 있습니다.

여기서 `Stream.toList()`는 Java 16부터 사용할 수 있으며, 반환된 리스트에는 요소를 추가하거나 삭제할 수 없습니다. 다만 리스트에 담긴 객체까지 모두 불변으로 만드는 것은 아닙니다.

또한 컬렉션의 Stream에서 실행하는 필터링은 이미 가져온 데이터를 Java에서 처리하는 것입니다. 데이터가 많다면 전체 조회 후 필터링하기보다, DB 조회 조건과 페이징을 먼저 적용할 수 있는지 검토해야 합니다.

## 3. 잘못 사용했을 때 생기는 문제

**Stream 안에서 DB 조회나 외부 API 호출을 반복하면, 코드가 짧아도 실제 처리 비용은 커질 수 있습니다.**

예를 들어 주문 1,000건을 처리하면서 주문마다 관련 상품을 DB에서 한 번씩 추가 조회한다면, 주문 조회 외에 1,000번의 추가 쿼리가 실행될 수 있습니다.

```text
주문 목록 조회
→ 주문 1의 상품 조회
→ 주문 2의 상품 조회
→ ...
→ 주문 1,000의 상품 조회
```

이 문제의 원인은 Stream 자체가 아니라 **요소마다 외부 작업을 반복하는 처리 구조**입니다. 같은 로직을 일반 반복문으로 바꾸더라도 조회 횟수는 줄어들지 않습니다.

따라서 필요한 데이터를 한 번에 조회하거나, 일괄 조회한 결과를 매핑하는 방식 등을 검토해야 합니다. JPA에서는 연관관계에 접근할 때 추가 쿼리가 발생할 수도 있으므로, Stream 코드의 길이보다 실제 실행되는 SQL과 호출 횟수를 확인하는 것이 중요합니다.

또한 조건 분기와 예외 처리가 많아 Stream이 지나치게 복잡해진다면, 메서드를 분리하거나 일반 반복문으로 표현하는 편이 더 읽기 쉬울 수 있습니다.

## 4. parallelStream 사용 시 주의점

`parallelStream()`은 데이터를 나누어 여러 스레드에서 처리할 수 있게 합니다. 하지만 **병렬 처리라고 해서 항상 더 빠르거나 안전한 것은 아닙니다.**

작업을 나누고 결과를 합치는 데에도 비용이 들기 때문에, 데이터가 적거나 각 작업이 단순하면 순차 Stream보다 느릴 수 있습니다.

또한 여러 스레드가 같은 값을 수정하면 경쟁 상태가 발생할 수 있습니다. 예를 들어 병렬 처리 중 외부의 같은 `ArrayList`에 결과를 추가하면 값이 누락되거나 잘못된 결과가 나올 수 있습니다. 결과 수집에는 외부 리스트를 직접 수정하기보다 `toList()`나 적절한 `collect()` 연산을 사용하는 편이 좋습니다.

| 확인할 내용 | 판단 기준 |
|---|---|
| 데이터량과 작업 비용 | 작업 분할·병합 비용을 감수할 만큼 처리량이 충분한가 |
| 작업의 독립성 | 각 요소를 다른 요소의 처리 결과에 의존하지 않고 처리할 수 있는가 |
| 공유 상태 | 여러 스레드가 같은 객체나 컬렉션을 수정하지 않는가 |
| 외부 호출 | DB·API 호출이 몰리면서 연결 수나 처리 한도를 넘지 않는가 |
| 실제 성능 | 순차 처리와 비교했을 때 응답 시간과 처리량이 개선되는가 |

Spring에서는 트랜잭션 범위도 확인해야 합니다. 일반적인 `@Transactional` 트랜잭션은 현재 실행 스레드에 연결되므로, **병렬 Stream의 다른 작업 스레드에 같은 트랜잭션이 자동으로 전달된다고 가정하면 안 됩니다.**

따라서 DB 변경이나 외부 API 호출을 포함하는 로직은 실행 스레드와 트랜잭션 범위를 검토한 뒤 병렬 처리 여부를 결정해야 합니다.

## 5. 종합 사례 — 주문 처리와 재고 동시성

> 주문 서비스에서 동시에 많은 요청이 들어오고, 여러 스레드가 같은 재고 수량을 차감하는 과정에서 데이터가 맞지 않는 문제가 발생했습니다. Stream 관점에서 가능한 원인과 해결 방향은 무엇인가요?

주문 서비스에 요청이 많이 들어온다고 해서 Stream 자체가 바로 문제를 만드는 것은 아닙니다. 중요한 것은 **어떤 데이터를 처리하고, 그 과정에서 공유 상태를 변경하는지**입니다.

주문 목록을 DTO로 변환하거나 주문 번호를 추출하는 작업과, 실제 재고를 차감하는 작업은 구분해서 봐야 합니다.

예를 들어 재고 확인과 차감이 하나의 원자적인 작업으로 보호되지 않으면 다음과 같은 상황이 생길 수 있습니다.

```text
남은 재고: 1개

스레드 A → 재고가 1개인지 확인 → 주문 가능 판단
스레드 B → 재고가 1개인지 확인 → 주문 가능 판단

→ 두 주문 모두 처리될 수 있음
→ 실제 재고보다 많은 주문이 승인되는 문제 발생
```

이 문제는 `parallelStream()`뿐 아니라 여러 HTTP 요청이 동시에 처리되는 상황에서도 발생할 수 있습니다. 따라서 Stream을 순차 처리로 바꾸는 것만으로 서버 전체의 재고 동시성 문제가 해결되지는 않습니다.

| 상황 | 대응 방향 |
|---|---|
| 조회 결과를 필터링하거나 DTO로 변환 | 공유 상태를 변경하지 않는 처리 흐름으로 구성 |
| 같은 JVM의 공유 객체를 수정 | 같은 모니터를 사용하는 `synchronized` 또는 동일한 `Lock`으로 재고 확인·차감 구간 전체를 보호 |
| 여러 서버가 같은 DB 재고를 수정 | DB 수준의 잠금이나 조건부 갱신 등으로 동시성 제어 |
| 요소마다 DB·API를 반복 호출 | 일괄 조회, 호출 수 제한, 처리 단위 조정 검토 |

`synchronized`나 `Lock`은 **같은 JVM에서 동일한 락을 사용하는 스레드 사이**의 접근을 제어합니다. 여러 서버가 같은 DB를 수정하는 환경에서는 JVM 내부의 락만으로 충분하지 않습니다.

또한 스레드 수를 늘리는 것은 재고 처리의 원자성을 보장하지 않습니다. 동시 작업이 많아지면 DB 연결이나 락을 기다리는 작업도 늘어날 수 있으므로, 병렬화 여부와 동시 실행량을 함께 검토해야 합니다.

Stream은 데이터 처리 흐름을 명확하게 표현하는 데 사용하고, 재고 변경처럼 데이터 일관성이 중요한 작업은 트랜잭션과 동시성 제어 범위를 별도로 설계해야 합니다.
