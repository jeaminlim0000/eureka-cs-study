## 1. 핵심 개념

### Race Condition과 Critical Section

여러 실행 흐름(프로세스, 스레드, 혹은 여러 서버)이 **같은 공유 자원**에 동시에 접근할 때, 접근 순서에 따라 결과가 달라지는 상황을 **경쟁 조건(Race Condition)**이라 한다. 이 문제가 발생할 수 있는 코드 구간을 **임계 영역(Critical Section)**이라 부른다.

```
스레드 A: 값 읽기(10) → 계산(10-3=7) → 값 쓰기(7)
스레드 B: 값 읽기(10) → 계산(10-5=5) → 값 쓰기(5)
```

A와 B가 동시에 값을 읽고 각자 계산해서 쓰면, 먼저 쓴 결과가 나중에 쓴 결과로 그냥 덮어써진다. 실제로는 두 연산이 모두 반영된 2가 남아야 하는데 5만 남는 식의 정합성 붕괴가 생긴다. 이걸 막으려면 **"임계 영역에는 한 번에 하나의 실행 흐름만 들어갈 수 있다"**는 보장이 필요하고, 이 보장을 제공하는 메커니즘이 Lock이다. Lock이 이루는 이 성질을 **상호 배제(Mutual Exclusion)**라 한다.

### Lock의 두 가지 기본 형태 — Mutex와 Semaphore

- **Mutex(Mutual Exclusion)**: 임계 영역에 **오직 하나의 실행 흐름만** 들어갈 수 있게 하는 락. 이진(binary) 상태(잠김/열림)를 가진다.
- **Semaphore**: 임계 영역에 **동시에 N개까지** 들어갈 수 있게 허용하는 락. 내부에 카운터를 두고, 진입할 때마다 카운터를 감소시키고 나갈 때 증가시킨다. 카운터가 1이면 Mutex와 동일한 효과를 낸다.

둘의 차이는 "몇 명까지 동시에 허용하는가"다. DB 커넥션 풀처럼 "동시에 최대 N개 연결만 허용"하는 상황은 세마포어의 전형적인 활용이고, "이 계좌 잔액은 한 번에 한 스레드만 수정 가능"한 상황은 뮤텍스의 전형적인 활용이다.

### Lock이 구현되는 계층 — 하드웨어부터 분산 시스템까지

Lock은 특정 언어의 기능이 아니라, 컴퓨팅 시스템의 여러 층위에서 각자의 방식으로 구현되는 범용 개념이다.

**① 하드웨어 계층 — 원자적 명령어(Atomic Instruction)**

CPU는 `Compare-And-Swap(CAS)`, `Test-And-Set` 같은, **중간에 다른 명령어가 끼어들 수 없이 통째로 실행되는(원자적) 명령어**를 제공한다. 모든 상위 계층의 락(Mutex, Semaphore 등)은 결국 이 원자적 명령어를 기반으로 구현된다. CAS는 "현재 값이 내가 예상한 값과 같으면 새 값으로 바꾸고, 다르면 실패로 알려달라"는 식으로 동작하며, 이를 이용하면 락을 아예 걸지 않고도(lock-free) 동시성 문제를 해결할 수 있는 알고리즘을 만들 수 있다.

**② 운영체제 계층 — 뮤텍스, 세마포어, 모니터**

OS는 커널이 관리하는 뮤텍스/세마포어 객체를 제공한다. 락을 획득하지 못한 스레드는 무한정 CPU를 소모하며 기다리지 않고(Busy-Wait), OS 스케줄러에 의해 대기 상태로 전환되어 CPU를 다른 작업에 양보한다. 락이 풀리면 OS가 대기 중이던 스레드를 다시 깨운다. 리눅스의 `futex(fast userspace mutex)`가 대표적인 구현이다.

**③ 언어/런타임 계층 — 모니터, 명시적 락 객체**

프로그래밍 언어는 위 OS 기능을 감싸서 더 쓰기 편한 형태로 제공한다. Java의 `synchronized`(모니터 기반), C++11의 `std::mutex`, Python의 `threading.Lock` 등이 이 계층이다.

**④ 데이터베이스 계층 — 비관적 락 / 낙관적 락**

여러 트랜잭션이 같은 row를 동시에 수정하는 문제를 다루기 위해 DB는 자체적인 락 메커니즘을 갖는다.

- **비관적 락(Pessimistic Lock)**: "충돌이 자주 일어날 것"이라 가정하고, 데이터를 읽는 시점에 아예 락을 걸어 다른 트랜잭션의 접근을 차단한다(`SELECT ... FOR UPDATE`).
- **낙관적 락(Optimistic Lock)**: "충돌이 드물 것"이라 가정하고, 평소엔 락을 걸지 않다가 실제로 저장하는 시점에 버전(또는 타임스탬프)을 비교해 그 사이 다른 트랜잭션이 값을 바꿨는지 확인한다. 바뀌었으면 실패로 처리하고 재시도한다.

**⑤ 분산 시스템 계층 — 분산 락(Distributed Lock)**

여러 대의 서버(각각 별도의 프로세스, 별도의 메모리 공간)가 공유 자원 하나를 두고 경쟁하는 경우, 단일 프로세스 안의 락(모니터, 뮤텍스)은 전혀 소용이 없다. 이때는 Redis, ZooKeeper, etcd처럼 **모든 서버가 공통으로 바라보는 외부 저장소**에 "내가 지금 이 자원을 쓰고 있다"는 표식을 남기고, 그 표식의 존재 여부로 락 상태를 판단하는 분산 락을 사용한다.

### 락 설계에서 함께 알아야 할 개념

- **재진입성(Reentrancy)**: 이미 락을 획득한 스레드가 같은 락을 다시 요청했을 때 스스로 블로킹되지 않고 통과시켜주는 성질. 재귀 호출이나 같은 락으로 보호된 메서드를 내부에서 또 호출하는 상황에 필요하다.
- **공정성(Fairness)**: 락을 기다리는 여러 스레드 중 누구에게 우선권을 줄 것인가. 공정한 락은 가장 오래 기다린 순서대로 락을 준다(FIFO에 가까움). 대신 순서를 관리하는 오버헤드 때문에 처리량은 다소 떨어질 수 있다.
- **락의 입도(Granularity)**: 락이 보호하는 범위의 크기. 테이블 전체에 락 하나를 거는 것(coarse-grained)은 단순하지만 동시성이 크게 떨어지고, row 단위·버킷 단위처럼 잘게 쪼개서 거는 것(fine-grained)은 동시 처리량은 높아지지만 구현이 복잡해지고 데드락 위험도 커진다.

## 2. Java / Spring에서의 Lock

### synchronized의 내부 동작 — 모니터와 락 승급

Java의 모든 객체는 헤더에 락 상태를 기록할 수 있는 영역(Mark Word)을 갖고 있고, `synchronized`는 이 객체가 내장한 **모니터(Monitor)**를 획득하는 방식으로 동작한다. HotSpot JVM은 `synchronized`의 성능을 위해 경합 정도에 따라 락을 단계적으로 승급시키는 최적화를 적용한다. 경합이 거의 없는 상황에서는 CAS 연산만으로 가볍게 락을 표시하는 **경량 락(Lightweight Lock)**으로 처리하다가, 경합이 심해져 여러 스레드가 동시에 기다리게 되면 OS 수준의 모니터 큐에 스레드를 재우는 **중량 락(Heavyweight Lock)**으로 전환된다. 이 전환을 **락 인플레이션(Lock Inflation)**이라 부른다.

`synchronized`는 락 획득과 해제가 컴파일러/JVM에 의해 자동으로 보장되며, 블록을 벗어나는 순간(정상 종료든 예외든) 반드시 해제된다는 게 가장 큰 안전성이다. 반면 `ReentrantLock`은 `lock()`과 `unlock()`을 개발자가 직접 호출해야 하므로 반드시 `try-finally`로 감싸야 하지만, 그 대가로 `tryLock()`(즉시 포기 또는 타임아웃), `lockInterruptibly()`(대기 중 인터럽트 허용), 하나의 락에 여러 대기 조건을 둘 수 있는 `Condition` 객체, 공정성 모드 설정처럼 `synchronized`에는 없는 세밀한 제어 기능을 제공한다.

### Spring Bean의 싱글톤 특성과 Lock의 관계

스프링 빈은 기본 스코프가 싱글톤이라, 하나의 `@Service`/`@Component` 인스턴스를 애플리케이션 내 모든 요청 스레드가 공유한다. 이 말은 그 빈의 인스턴스 필드에 `synchronized`를 걸면, 그 서버 프로세스로 들어오는 모든 요청(스레드)이 실제로 같은 락 객체를 두고 경쟁하게 된다는 뜻이다. 이는 의도한 대로 동작하는 것이지만, 동시에 스프링 빈을 무상태(stateless)로 설계하라는 일반적인 권장과는 긴장 관계에 있다. 인스턴스 필드에 공유 상태를 두고 락으로 보호하는 패턴은, 서버가 한 대일 때는 동작하더라도 인스턴스를 여러 대로 늘리는 순간 각 서버가 별도의 JVM·별도의 빈 인스턴스를 가지므로 더 이상 전체 시스템의 동시성을 보장하지 못한다.

### @Transactional과 synchronized를 함께 쓸 때의 순서 문제

스프링에서 자주 놓치는 지점이다. `@Transactional`이 붙은 메서드는 실제로는 AOP 프록시가 감싸서, 원래 메서드 호출이 끝난 뒤 프록시 코드가 트랜잭션을 커밋한다. 만약 그 메서드 내부에 `synchronized`를 걸어두면, `synchronized` 블록은 메서드 실행이 끝나는 시점에 즉시 풀리지만, 실제 DB 커밋은 프록시가 메서드 밖에서 그 이후에 수행한다. 그 결과 **락이 풀린 시점과 데이터가 실제로 DB에 반영되는 시점 사이에 틈이 생긴다.** 그 틈에 다른 스레드가 락이 풀린 걸 보고 진입해 아직 커밋되지 않은(이전) 값을 읽어버리면, 락을 걸었음에도 정합성이 깨지는 결과로 이어질 수 있다. 이 문제는 락의 범위를 트랜잭션 범위와 정확히 일치시키거나, 애초에 애플리케이션 레벨 락 대신 DB 트랜잭션이 직접 보장하는 락(비관적/낙관적 락)으로 옮기는 방식으로 해결한다.

### JPA의 낙관적 락과 예외 처리 흐름

스프링 데이터 JPA에서 `@Version` 필드로 낙관적 락을 걸면, 트랜잭션이 엔티티를 저장하는 시점에 조회했던 버전과 현재 버전이 다르면 예외가 발생하며 트랜잭션이 롤백된다. 이 예외는 그 자체로 요청을 실패시키는 게 아니라, "누군가 먼저 수정했으니 최신 상태를 다시 읽고 다시 시도하라"는 신호로 다뤄야 한다. 그래서 낙관적 락을 쓰는 코드는 보통 이 예외를 잡아 일정 횟수만큼 재시도하는 구조를 함께 둔다. 스프링에서는 이런 재시도 로직을 매번 직접 작성하는 대신, 재시도 정책을 선언적으로 적용해주는 기능(스프링 리트라이 계열 기능)을 결합해 처리하는 경우가 많다.

### 비관적 락과 트랜잭션 격리 수준의 관계

JPA의 비관적 락(`PESSIMISTIC_WRITE`)은 내부적으로 DB의 `SELECT ... FOR UPDATE`를 실행해, 해당 트랜잭션이 끝날 때까지 다른 트랜잭션이 그 row에 손대지 못하게 막는다. 이는 트랜잭션의 격리 수준(Isolation Level)과 함께 맞물려 동작하는데, 격리 수준이 어떻게 설정되어 있든 명시적인 `FOR UPDATE` 락은 그와 별개로 해당 row에 대한 배타적 접근을 강제한다는 점에서, 격리 수준만으로는 못 막는 동시 수정 문제를 보완하는 역할을 한다. 다만 트랜잭션이 길어질수록(예: 락을 잡은 채로 외부 API를 호출하는 등) 그 시간만큼 다른 요청들이 대기하게 되므로, 비관적 락을 건 트랜잭션은 최대한 짧게 유지해야 한다.

### 분산 락을 스프링에 도입하는 방식

여러 서버 인스턴스로 확장된 환경에서 애플리케이션 레벨 락이 무의미해지는 문제는 앞서 계층별 정리에서 다뤘다. 스프링에서는 보통 Redis 기반의 분산 락 클라이언트를 연동해 이 문제를 해결하는데, 매번 락 객체를 직접 획득·해제하는 코드를 반복해서 작성하기보다 AOP 기반의 커스텀 어노테이션으로 감싸서 사용하는 패턴이 실무에서 흔하다. 메서드에 어노테이션 하나만 붙이면 그 메서드 실행 전후로 자동으로 락을 획득·해제하도록 만드는 방식으로, 비즈니스 로직과 락 관리 코드를 분리해 가독성과 재사용성을 높인다. 이 경우도 앞서 다룬 `@Transactional` 순서 문제와 유사하게, 분산 락의 해제 시점과 트랜잭션 커밋 시점의 순서를 정확히 맞추는 것이 설계에서 중요한 포인트가 된다.

### @Async와 Lock을 함께 쓸 때의 주의점

`@Async`로 비동기 실행되는 메서드는 호출한 스레드가 아니라 별도의 스레드 풀에서 실행된다. 만약 호출부에서 락을 획득한 채로 `@Async` 메서드를 호출하고, 그 비동기 메서드의 완료 결과를 동기적으로 기다리는 구조를 짜면, 호출 스레드는 락을 쥔 채 비동기 작업의 완료를 기다리고, 비동기 작업을 실행할 스레드 풀은 다른 이유로 가득 차 있어 시작조차 못 하는 상황이 겹치면 서로를 기다리는 교착 상태에 가까운 지연이 발생할 수 있다. 락을 쥔 채로 비동기 경계를 넘나드는 설계는 가능한 한 피하고, 락으로 보호해야 하는 임계 영역은 하나의 실행 흐름 안에서 최대한 짧게 끝내는 것이 안전하다.

## 3. 잘못 사용했을 때 생기는 문제

**트랜잭션 커밋 전에 락이 먼저 풀리는 문제**

앞서 다룬 것처럼, `synchronized`와 `@Transactional`을 같은 메서드에 걸었을 때 AOP 프록시의 트랜잭션 커밋이 락 해제보다 나중에 일어나면서, 락이 풀린 직후부터 실제 커밋 전까지의 짧은 틈에 다른 스레드가 오래된 값을 읽어가는 문제가 생길 수 있다. 락을 걸었는데도 동시성 버그가 재현된다면 가장 먼저 의심해봐야 하는 패턴이다.

**싱글톤 빈의 상태 공유를 스케일 아웃 이후까지 유효하다고 착각**

단일 서버에서 개발하고 테스트할 때는 인스턴스 필드 + `synchronized` 조합이 문제없이 동작하기 때문에, 이 방식이 서버 대수와 무관하게 항상 안전하다고 오해하기 쉽다. 트래픽이 늘어 서버를 여러 대로 늘리는 순간, 각 서버는 서로 다른 락을 갖게 되어 동시성 문제가 그대로 재발한다.

**낙관적 락 예외를 재시도 없이 그대로 사용자 오류로 내려보냄**

`OptimisticLockException` 계열 예외가 발생했을 때, 이를 "누군가 먼저 수정했으니 다시 시도하면 되는 정상적인 흐름"으로 다루지 않고 그냥 500 에러로 응답을 내려버리면, 실제로는 충분히 성공할 수 있었던 요청이 사용자에게 실패로 노출된다. 재시도 로직 없이 낙관적 락만 도입하면 오히려 사용자 경험이 나빠질 수 있다.

**비관적 락을 잡은 트랜잭션이 지나치게 길어짐**

락을 잡은 트랜잭션 안에서 외부 API 호출이나 느린 연산을 함께 수행하면, 그 자원에 접근하려는 다른 모든 요청이 그 시간만큼 통째로 대기한다. 락의 존재 자체보다 락을 쥐고 있는 시간이 길어지는 것이 실무에서는 더 흔하고 치명적인 성능 문제로 이어진다.

**분산 락에 TTL을 설정하지 않음**

분산 락을 획득한 서버 인스턴스가 처리 도중 예외 없이 그대로 죽어버리면, 락 해제 코드(`finally`의 `unlock()`)가 실행될 기회 자체가 없다. TTL이 없는 분산 락은 이 경우 영원히 풀리지 않고, 다른 모든 서버가 그 자원에 대해 무한정 대기하게 되는 심각한 장애로 이어질 수 있다.

**ReentrantLock의 unlock 누락**

`lock()` 이후의 코드에서 예외가 발생했는데 `unlock()`이 `try-finally` 밖에 있거나 빠져 있으면, 그 락은 영원히 해제되지 않는다. `synchronized`는 언어 차원에서 이 문제를 자동으로 막아주지만, `ReentrantLock`은 개발자가 직접 이 책임을 져야 한다는 점을 코드 리뷰에서 특히 주의 깊게 봐야 한다.

## 4. 면접 질문

**Q. `@Transactional`이 붙은 메서드 안에서 `synchronized`로 동시성 문제를 막으려 했는데도 여전히 데이터 정합성이 깨지는 경우가 있다. 왜 그런 일이 생기는가?**

A. `@Transactional`은 AOP 프록시가 메서드 호출을 감싸는 방식으로 동작해, 실제 커밋은 메서드 실행이 끝난 뒤 프록시 코드에서 이루어진다. 반면 `synchronized` 블록은 메서드 실행이 끝나는 즉시 풀린다. 그 결과 락이 해제되는 시점과 트랜잭션이 실제로 커밋되어 다른 트랜잭션에서 변경 사항이 보이게 되는 시점 사이에 틈이 생기고, 그 틈에 다른 스레드가 진입해 아직 반영되지 않은 이전 값을 읽어가면서 정합성이 깨질 수 있다.

## 5. 종합 사례 — 주문 처리와 재고 동시성

> 주문 서비스에서 동시에 많은 요청이 들어오고, 여러 스레드가 같은 재고 수량을 차감하는 과정에서 데이터가 맞지 않는 문제가 발생했습니다. Lock 관점에서 어떤 방식으로 해결할 수 있는가?

재고 확인과 차감이 하나의 임계 영역으로 보호되지 않으면, 두 스레드가 거의 동시에 "재고 1개 남음"을 확인하고 둘 다 주문을 승인해버리는 경쟁 조건이 발생한다. Lock은 이 임계 영역에 한 번에 하나의 실행 흐름만 들어가도록 보장해 문제를 해결한다.

| 서버 구성 | 적용 가능한 Lock | 주의점 |
|---|---|---|
| 단일 서버(단일 JVM) | `synchronized` 또는 `ReentrantLock`으로 재고 확인+차감 구간 전체를 감싼다 | 락 범위가 트랜잭션 커밋 시점까지 포함하도록 맞춰야 함(앞서 다룬 `@Transactional` 순서 문제) |
| 다중 서버(여러 JVM) | Redis 등 외부 저장소 기반 분산 락 | TTL을 반드시 설정해 서버 장애 시 영구 대기를 방지 |
| DB 접근 경쟁이 핵심일 때 | 비관적 락(`SELECT ... FOR UPDATE`) 또는 낙관적 락(`@Version`) | 비관적 락은 트랜잭션을 짧게, 낙관적 락은 충돌 시 재시도 로직을 함께 둔다 |

`synchronized`나 `ReentrantLock`은 같은 JVM 안에서만 유효하므로, 서버를 여러 대로 늘리는 순간 각 서버가 별도의 락을 갖게 되어 보호가 무력화된다. 이 경우 분산 락이나 DB 수준의 락으로 범위를 옮겨야 하며, 어떤 방식을 택하든 "락을 쥐고 있는 시간"을 최소화하는 설계가 함께 필요하다.
