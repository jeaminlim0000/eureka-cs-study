# Week11 Java Core — JVM

> 발표자: 조현빈　 발표일: 2026.09.22　 주차 Issue: [#[이슈번호]]([이슈 링크])

## 1. 핵심 개념

JVM은 자바 바이트코드를 실행하는 가상 머신이다. 자바가 "Write Once, Run Anywhere"를 실현할 수 있는 이유는, 실제 OS·하드웨어와 직접 맞닿는 대상이 자바 코드가 아니라 JVM이기 때문이다. 개발자는 항상 동일한 JVM 스펙 위에서만 코드를 실행하면 되고, JVM 자체가 OS별로 다르게 구현되어 있어서 플랫폼 차이를 흡수해준다.

JVM은 크게 세 가지 축으로 구성된다.

- **Class Loader Subsystem**: `.class` 파일(바이트코드)을 메모리로 읽어들이는 부분
- **Runtime Data Area**: 실행 중 사용하는 메모리 영역(Heap, Stack, Metaspace 등)
- **Execution Engine**: 바이트코드를 실제로 실행하는 부분(인터프리터, JIT 컴파일러, GC 포함)

## 2. 실행 흐름과 구성 요소

### 전체 실행 흐름

자바 코드가 실행되기까지 거치는 단계는 다음과 같다.

```
1. .java 소스 파일 작성
2. javac(자바 컴파일러)가 컴파일 → .class 파일(바이트코드) 생성
   (OS/하드웨어에 종속되지 않는 중간 코드 상태)
3. java 명령 실행 → JVM 구동
4. Class Loader가 .class 파일을 읽어 JVM 메모리(Runtime Data Area)에 적재
5. Execution Engine이 바이트코드를 실행
   - 처음엔 인터프리터가 한 줄씩 해석 실행
   - 자주 실행되는 부분(Hot Spot)은 JIT 컴파일러가 네이티브 코드로 변환
6. 실행 중 GC가 백그라운드에서 더 이상 참조되지 않는 객체를 회수
```

핵심은 javac이 소스를 기계어로 바로 컴파일하는 게 아니라 바이트코드까지만 컴파일한다는 점이다. 실제 기계어로의 변환(또는 해석 실행)은 실행 시점에 JVM 내부에서 일어난다. C/C++ 같은 네이티브 컴파일 언어와 근본적으로 다른 지점이다. 기계어까지 바로 컴파일하지 않고 바이트코드라는 중간 단계를 둠으로써 다음과 같은 이점을 얻는다.

- **플랫폼 독립성**: 바이트코드는 특정 OS나 CPU 아키텍처에 종속되지 않는다. 곧바로 기계어로 컴파일한다면 Windows용·Linux용·macOS용 기계어를 각각 만들어 배포해야 하지만, 바이트코드 하나만 만들어두면 그걸 실행할 JVM만 각 플랫폼에 맞게 준비되어 있으면 어디서든 동일하게 실행된다.
- **런타임 최적화 여지 확보**: 컴파일 시점에는 알 수 없는 정보(실제로 어떤 메서드가 얼마나 자주 호출되는지, 어떤 분기가 자주 타는지)를 JVM이 실행하면서 직접 관찰할 수 있다. 이를 바탕으로 JIT 컴파일러가 진짜 자주 쓰이는 부분만 골라 네이티브 코드로 변환한다. 반면 정적 컴파일(AOT)은 이런 실행 시점의 실제 패턴을 반영하지 못하고 컴파일 시점의 짐작만으로 최적화해야 한다.
- **실행 전 검증(Verify) 가능**: 바이트코드는 JVM이 로딩 시점에 형식이 올바른지, 스택 조작 방식이 안전한지 등을 검사할 수 있는 표준화된 형태다. 조작되거나 잘못 생성된 바이트코드가 시스템을 손상시키는 걸 막는 보안 계층 역할을 한다. 바로 기계어였다면 이런 중간 검증 자체가 불가능하다.
- **언어 독립적인 실행 환경**: 바이트코드라는 공통 규격만 지키면 어떤 언어의 컴파일러든 그 결과물을 JVM 위에서 실행할 수 있다. Kotlin, Scala, Groovy 등이 자바 소스를 거치지 않고 각자의 컴파일러로 바이트코드를 만들어 JVM에서 실행되는 것도 이 덕분이다.
- **가볍고 빠른 컴파일**: 바이트코드로의 변환은 기계어로의 완전한 최적화 컴파일보다 훨씬 단순한 작업이라 `javac` 실행 자체가 빠르다. 무거운 최적화 작업은 실제로 그게 필요한(자주 실행되는) 코드에 한해, 실행 중에 JIT이 담당하도록 미뤄진 것이다.

### Class Loader

`.class` 파일을 찾아서 JVM 메모리(Method Area)에 로드하고, 링크하고, 초기화하는 과정을 담당한다. 클래스 로더는 3단계 계층 구조를 이룬다.

```
Bootstrap Class Loader (최상위)
    ↓
Extension(Platform) Class Loader
    ↓
Application(System) Class Loader
```

- Bootstrap Class Loader: JVM 구동 시 가장 먼저 실행. JDK 핵심 클래스(java.base 등)를 로드. 네이티브 코드로 구현되어 자바 코드로는 접근 불가.
- Extension(Platform) Class Loader: 확장 라이브러리를 로드.
- Application(System) Class Loader: 개발자가 작성한 클래스, classpath에 지정된 클래스들을 로드. 대부분의 자체 작성 클래스가 여기서 로드됨.

클래스 로딩 요청이 오면, 자기가 먼저 로드하지 않고 상위 로더에게 먼저 위임하는 **위임 모델(Parent Delegation Model)**을 따른다. 상위 로더가 못 찾으면 그제서야 자신이 로드를 시도한다. 이렇게 하면 개발자가 실수로 `java.lang.String` 같은 이름으로 클래스를 만들어도, 항상 Bootstrap이 로드한 진짜 `java.lang.String`이 우선권을 가져 핵심 API의 무결성이 보장되고, 같은 클래스의 중복 로드도 방지된다.

클래스 로딩 자체는 세부적으로 3단계로 나뉜다.

1. **Loading**: `.class` 파일을 찾아 바이너리 데이터를 읽고, Method Area에 클래스 메타정보(필드, 메서드, 상수 등)를 저장하고, Heap에 해당 클래스를 대표하는 `Class` 객체를 생성한다.
2. **Linking**: Verify(바이트코드가 JVM 명세를 위반하지 않는지 검사) → Prepare(static 필드를 위한 메모리를 할당하고 기본값 0/null/false로 초기화) → Resolve(심볼릭 레퍼런스를 실제 메모리 주소 참조로 변환, 일부는 실제 사용 시점까지 지연됨)의 3단계로 구성된다.
3. **Initialization**: static 변수에 코드에 명시된 실제 값을 대입하고, static 초기화 블록을 실행한다. 이 시점에 비로소 클래스가 능동적으로 사용 가능한 상태가 된다.

### Runtime Data Area

JVM이 실행 중 사용하는 메모리는 스레드가 공유하는 영역과 스레드마다 독립적인 영역으로 나뉜다.

```
[스레드 공유 영역]              [스레드별 독립 영역]
Heap                            Stack (JVM Stack)
Method Area (Metaspace)         PC Register
                                 Native Method Stack
```

- **Heap**: 객체(인스턴스)와 배열이 저장되는 공간. `new`로 생성한 모든 객체가 들어간다. GC의 주 대상이 되는 영역이며, 모든 스레드가 공유한다.
- **Stack**: 스레드마다 하나씩 독립적으로 생성된다. 메서드가 호출될 때마다 Stack Frame이 push되고 종료 시 pop된다. 기본 타입 지역 변수와 객체의 레퍼런스(주소값)가 여기 저장되며, 실제 객체 본체는 Heap에 있다. 재귀 호출이 과도하게 깊어지면 `StackOverflowError`가 발생한다.
- **Metaspace(Method Area)**: 클래스의 메타정보(구조, 메서드/필드 정보, static 변수, 런타임 상수 풀)가 저장된다. Java 7까지는 Heap 내부의 `PermGen`이 이 역할을 했지만, Java 8부터 Metaspace로 대체됐다. PermGen은 Heap 내부의 고정 크기 영역이라 클래스 메타데이터가 많이 쌓이는 애플리케이션에서 `OutOfMemoryError: PermGen space`가 자주 발생하는 문제가 있었는데, Metaspace는 OS가 관리하는 Native Memory를 사용하고 기본적으로 크기 제한이 없어(시스템 메모리가 허용하는 한 자동 확장) 이 문제를 크게 완화했다.
- **PC(Program Counter) Register**: 스레드마다 독립적으로 존재하며, 현재 실행 중인 바이트코드 명령어의 주소를 가리킨다. 스레드가 Context Switching 후 다시 실행될 때 어디서부터 이어갈지 이 값으로 판단한다.
- **Native Method Stack**: 자바가 아닌 네이티브 코드(JNI로 호출되는 C/C++ 코드)를 실행할 때 사용하는, 자바용 Stack과 별개인 스택이다.

### JIT(Just-In-Time) Compiler

JVM은 기본적으로 바이트코드를 인터프리터 방식으로 한 줄씩 해석 실행한다. 이식성은 좋지만 매번 해석하는 오버헤드 때문에 네이티브 코드보다 느리다. JIT 컴파일러는 실행 중 자주 호출되는 코드(Hot Spot)를 실시간으로 감지해 그 부분을 네이티브 기계어로 컴파일해서 캐싱해두고, 이후 호출부터는 컴파일된 코드를 바로 실행한다.

```
처음 몇 번 실행: 인터프리터로 해석 실행 (동시에 실행 횟수 카운트)
        ↓
호출 횟수가 임계치를 넘으면 (Hot Spot으로 판단)
        ↓
JIT 컴파일러가 백그라운드 스레드에서 네이티브 코드로 컴파일
        ↓
이후 호출부터는 컴파일된 네이티브 코드로 직접 실행
```

오라클 공식 JVM 구현체의 이름이 HotSpot VM인 것도 이 전략에서 따온 것이다. 내부에는 두 가지 컴파일러가 있다.

- C1(Client Compiler): 컴파일 속도가 빠르고 최적화 수준은 상대적으로 낮다. 빠른 웜업이 필요한 상황에 적합하다.
- C2(Server Compiler): 컴파일은 느리지만 인라이닝, 루프 최적화 같은 정교한 최적화를 적용해 최종 성능이 더 좋다. 오래 실행되는 서버 애플리케이션에 적합하다.

Java 7부터는 이 둘을 단계적으로 섞어 쓰는 **Tiered Compilation**이 기본 동작이다. 처음엔 C1으로 빠르게 컴파일해 초반 응답성을 확보하고, 정말 자주 실행되는 극소수 핵심 코드만 C2로 재컴파일해 최종 성능을 극대화한다. 이 외에 짧은 메서드 호출을 호출부에 직접 삽입하는 인라이닝(Inlining), 객체가 메서드 바깥으로 탈출하지 않으면 Heap 대신 Stack에 할당하거나 할당 자체를 생략하는 탈출 분석(Escape Analysis) 같은 최적화도 함께 수행한다.

## 3. 자주 생기는 문제나 실수

- **PermGen 시절의 OOM**: Java 7까지 클래스 메타데이터가 Heap 내부 고정 영역(PermGen)에 쌓여, 리플렉션·동적 프록시를 많이 쓰는 애플리케이션에서 `OutOfMemoryError: PermGen space`가 자주 발생했다. Java 8 이후 Metaspace로 바뀌면서 완화됐지만, 클래스 로더 누수가 있으면 Metaspace도 계속 커진다.
- **JIT 워밍업 구간의 성능 착각**: 애플리케이션 기동 직후에는 인터프리터와 C1 위주로 실행되므로, 짧은 부하 테스트 결과를 그대로 운영 성능으로 해석하면 오판하기 쉽다.

## 4. 면접 질문

**Q1. 자바가 "Write Once, Run Anywhere"를 구현할 수 있는 이유는 JVM의 어떤 특성 때문인가?**

A. 자바 컴파일러(javac)는 소스 코드를 특정 OS의 기계어가 아니라 OS에 독립적인 중간 표현인 바이트코드로 컴파일한다. 이 바이트코드를 실제 실행 가능한 형태로 처리하는 것은 각 플랫폼에 맞게 구현된 JVM의 몫이다. 즉 OS별로 다른 것은 자바 프로그램이 아니라 JVM 쪽이고, 개발자는 항상 동일한 JVM 스펙 위에서만 작업하면 되기 때문에 플랫폼 독립성이 확보된다.

**Q2. Java 8에서 PermGen이 Metaspace로 바뀐 이유는 무엇인가?**

A. PermGen은 Heap 내부의 고정 크기 영역이라, 클래스 메타데이터가 많이 쌓이는 애플리케이션(리플렉션·동적 프록시를 많이 쓰는 프레임워크 등)에서 `OutOfMemoryError: PermGen space`가 자주 발생하는 구조적 문제가 있었다. Metaspace는 Heap이 아니라 OS가 관리하는 Native Memory를 사용하고 기본적으로 크기 제한이 없어서(시스템 메모리 허용 범위까지 자동 확장) 이 문제를 크게 완화했다.

**Q3. JIT 컴파일러가 있는데도 왜 JVM은 처음부터 모든 코드를 네이티브 코드로 컴파일하지 않고 인터프리터로 시작하는가?**

A. 모든 코드를 미리 컴파일(AOT 방식)하면 애플리케이션 시작 시간이 크게 늘어나고, 실제로는 거의 실행되지 않는 코드까지 컴파일하는 데 리소스를 낭비하게 된다. 인터프리터로 우선 실행하면서 어떤 코드가 실제로 자주 호출되는지(Hot Spot) 프로파일링 정보를 수집하고, 그 정보를 바탕으로 정말 이득이 큰 부분만 선별적으로 컴파일하는 편이 전체적으로 더 효율적이기 때문이다.

## 5. 종합 사례 — 트래픽 증가 후 응답 지연과 OOM

> 트래픽이 증가한 Spring 서버에서 응답 시간이 길어지고 `OutOfMemoryError`가 발생했을 때, JVM 메모리 구조 관점에서 가능한 원인과 확인 방향은 무엇인가?

OOM 메시지만으로는 문제를 바로 특정할 수 없다. JVM이 메모리를 Heap, Stack, Metaspace 등으로 나눠 관리한다는 구조를 알아야, 에러 메시지에 붙는 영역 이름을 보고 실제 원인을 좁힐 수 있다.

| 에러 메시지 | 의심 영역 | 확인 방향 |
|---|---|---|
| `OutOfMemoryError: Java heap space` | Heap | 객체 참조가 계속 유지되는지, 캐시·컬렉션이 커지는지 확인 |
| `OutOfMemoryError: Metaspace` | Metaspace(Method Area) | 클래스 로더가 반복 생성·누수되는지 확인(동적 프록시, 리플렉션, 핫 리로드 등) |
| `OutOfMemoryError: unable to create new native thread` | Native Memory / Thread | 스레드 풀이 무한정 늘어나는지, OS 스레드 수 제한에 걸리는지 확인 |
| `StackOverflowError` | Stack | 재귀 호출 깊이, 스택 크기(`-Xss`) 설정 확인 |

트래픽 증가 직후 응답이 느려지는 현상은 OOM과 원인이 다를 수도 있다. 배포 직후에는 아직 JIT이 Hot Spot을 충분히 컴파일하지 못해 인터프리터 비중이 높은 **워밍업 구간**일 수 있으므로, 응답 지연의 시작 시점이 배포 직후인지 트래픽 증가 시점인지부터 구분해야 한다.

Metaspace가 원인인 경우는 Heap 튜닝(`-Xmx` 조정)으로는 해결되지 않는다. 클래스 로더 누수(요청마다 동적으로 클래스를 생성하는 라이브러리, 운영에 남은 핫 리로드 설정 등)를 찾아 제거해야 한다. 반대로 Heap 누수인데 Metaspace 설정만 늘리면 증상이 늦게 나타날 뿐 근본 원인은 그대로 남는다.
