## Page Fault

프로세스가 가상 메모리 주소에 접근했는데 해당 페이지가 물리 메모리(RAM)에 없을 때 발생합니다. CPU는 예외를 발생시키고, 운영체제는 디스크의 페이지를 RAM으로 가져온 뒤 중단된 명령을 다시 실행합니다.

```text
메모리 접근 → RAM에 페이지 없음 → Page Fault
→ 디스크 I/O로 페이지 적재 → 페이지 테이블 갱신 → 명령 재실행
```

디스크 I/O는 RAM 접근보다 훨씬 느리므로 Page Fault가 잦으면 서버 응답 시간이 크게 늘어날 수 있습니다. 메모리가 부족해 이미 있는 페이지를 계속 내보내고 다시 읽는 현상을 Thrashing이라고 합니다.

## Page Cache

Page Cache는 파일 또는 디스크 블록을 RAM에 캐시하는 운영체제 영역입니다. 애플리케이션이 파일을 다시 읽을 때 디스크까지 가지 않고 Page Cache에서 읽으면 I/O 비용이 줄어듭니다.

Java 서버가 DB, 로그 파일, 정적 파일을 다룰 때도 운영체제 Page Cache의 영향을 받습니다. JVM Heap만 보고 메모리를 모두 사용하면 OS Page Cache 공간이 부족해져 파일 I/O 성능이 나빠질 수 있습니다.

## 실무 연결

컨테이너 환경에서 JVM의 최대 Heap을 서버 메모리에 너무 가깝게 잡으면 JVM 외 메모리, OS Page Cache, 네이티브 메모리 공간이 부족해질 수 있습니다. 따라서 Heap 크기만 키우기보다 전체 메모리 여유와 Page Fault 증가 여부를 함께 봐야 합니다.

## 발표 중 확인한 질문

**Page Fault가 자주 발생하면 서버가 느려지는 이유를 설명해 주세요.**  
필요한 페이지가 RAM에 없어 디스크에서 읽어 와야 하기 때문입니다. 디스크 I/O 동안 실행 흐름이 지연되고, 메모리 부족으로 페이지 교체가 반복되면 Thrashing이 발생해 처리량이 감소할 수 있습니다.
